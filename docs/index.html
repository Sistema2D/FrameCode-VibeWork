1) Visão geral

FrameCode VibeWork é um framework de desenvolvimento assistido por IA orientado por documentação, criado para reduzir perda de contexto, controlar escopo e padronizar execução técnica entre humanos e agentes.

O que ele é

  • Um framework de governança operacional e técnica.
  • Uma estrutura de memória incremental baseada em Markdown.
  • Um padrão de trabalho com rastreabilidade completa por versão.

O que ele não é

  • Não é um framework de frontend/backend com runtime próprio.
  • Não substitui Git, revisão ou decisão arquitetural humana.
  • Não depende de scripts automáticos para governança.

2) Problema resolvido

Sessões com IA sofrem com perda de contexto, repetição de erros e mudanças sem trilha de auditoria. O framework estrutura esse processo para tornar a execução previsível e auditável.

Dor comumResposta no framework
Contexto se perde entre sessõesSíntese AICC em wiki/sessions/ e ingestão seletiva.
Escopo muda sem controleRegra obrigatória de plano em Plans/ antes de qualquer modificação.
Mudanças sem histórico claroChangelog versionado em changelogs/Vx.y.z.md.
Conhecimento técnico dispersoLLM Wiki estruturada em wiki/ (patterns, decisions, releases, sessions).

3) Ciclo de funcionamento

  1. Fase 0: briefing, escopo, stack e manifesto base.
  2. Solicitação: entrada de demanda (bug, feature, release, refactor).
  3. Planejamento: criação de plano com prioridade, risco, critérios e testes.
  4. Execução: mudanças limitadas ao escopo do plano.
  5. Registro: atualização de changelog e documentos impactados.
  6. Validação: testes proporcionais ao risco + auditoria documental.
  7. Memória: síntese da sessão e atualização da wiki quando houver aprendizado reutilizável.
Regra central: nenhuma alteração funcional, visual, estrutural ou documental deve ocorrer sem plano correspondente.

4) Arquitetura documental

A aplicação funciona como uma malha de documentos com responsabilidades explícitas.

5) Governança por planos

Fluxo obrigatório

  1. Criar plano em Plans/pending/.
  2. Mover para Plans/in_progress/ ao iniciar.
  3. Executar somente o escopo aprovado.
  4. Atualizar changelog da versão.
  5. Fechar plano em Plans/completed/ ou discontinued/.

Campos mínimos do plano

  • Prioridade P1..P5 e risco R1..R5
  • Versão atual e esperada
  • Critérios de aceite
  • Plano de testes
  • Status e evidências de validação

6) Versionamento e release

O framework segue Vx.y.z e exige changelog para toda mudança em arquivo versionado.

  • Major: quebra de compatibilidade, mudança arquitetural ampla.
  • Minor: novas capacidades e fluxos relevantes.
  • Patch: correções e melhorias documentais/processuais.
Estados de release: in_preparation, in_validation, published, canceled.
Uma versão só pode ser published quando os planos citados estiverem em Plans/completed/ e as validações estiverem registradas.

7) IA, AICC e ASE

AICC (compressão de contexto)

  • Gera síntese cronológica por sessão em wiki/sessions/S*.md.
  • Reduz custo de tokens com handoff estruturado.
  • Permite retomar trabalho sem reprocessar todo o repositório.

ASE (motor de habilidades)

  • Carrega skills sob demanda (JIT), não no prompt inicial.
  • Inclui habilidades de release, lint wiki, commits e formatação.
  • Melhora consistência e reduz ruído de contexto.

Referências: AI.md, CONTEXT_MAP.md, skills/README.md, wiki/schema.md.

8) Segurança e dados

  • Não versionar credenciais, dados privados e artefatos temporários.
  • Validar path traversal em qualquer leitura/escrita de caminhos dinâmicos.
  • Manter .env e variantes fora do versionamento (com .env.example permitido).
  • Registrar limitações ou riscos residuais ao fechar planos.

9) Validação e auditoria

A validação é proporcional ao risco e sempre precisa ser registrada com evidência.

RiscoNível mínimo esperado
R1 / R2Verificações locais + revisão de links/consistência.
R3Validação de fluxos compartilhados e regressão local.
R4 / R5Validações completas com foco em segurança, dados e rollback.

1) Overview

FrameCode VibeWork is a documentation-first framework for AI-assisted development, designed to reduce context loss, enforce scope control, and standardize technical execution across humans and agents.

What it is

  • An operational and technical governance framework.
  • An incremental memory system based on Markdown.
  • A work model with full version-level traceability.

What it is not

  • Not a frontend/backend runtime framework.
  • Not a replacement for Git review or human architectural decisions.
  • Not dependent on automation scripts for governance.

2) Problem solved

AI sessions often drift, repeat mistakes, and apply changes without audit trails. This framework structures the process to keep execution predictable and verifiable.

Common painFramework response
Session context gets lostAICC session synthesis in wiki/sessions/ plus selective ingestion.
Scope changes without controlMandatory plan rule in Plans/ before any modification.
Changes with unclear historyVersioned changelog in changelogs/Vx.y.z.md.
Scattered technical knowledgeStructured LLM Wiki in wiki/ (patterns, decisions, releases, sessions).

3) Operating lifecycle

  1. Phase 0: briefing, scope, stack, and baseline manifest.
  2. Request: incoming demand (bug, feature, release, refactor).
  3. Planning: create plan with priority, risk, acceptance criteria, and tests.
  4. Execution: apply changes strictly within plan scope.
  5. Recording: update changelog and impacted documents.
  6. Validation: risk-proportional tests plus documentation audit.
  7. Memory: session synthesis and wiki update for reusable knowledge.
Core rule: no functional, visual, structural, or document change without a corresponding plan.

4) Document architecture

The application operates as a documentation mesh with explicit responsibilities.

LayerFile / DirectoryResponsibility
OperationsAGENTS.mdPrimary execution guide for humans and AI.
IdentityMANIFEST.mdOfficial state, summarized scope, and key risks.
Change controlPlans/Lifecycle of each change.
Version historychangelogs/Formal per-version record.
Memorywiki/Incremental and navigable technical knowledge.
AI patternsskills/High-density checklists loaded on demand.
Templatesgovernance/Reusable empty structures for new projects.

5) Plan-driven governance

Mandatory flow

  1. Create plan in Plans/pending/.
  2. Move to Plans/in_progress/ when work starts.
  3. Execute only approved scope.
  4. Update version changelog.
  5. Close in Plans/completed/ or discontinued/.

Minimum plan fields

  • Priority P1..P5 and risk R1..R5
  • Current and expected version
  • Acceptance criteria
  • Test plan
  • Status and validation evidence

6) Versioning and release

The framework follows Vx.y.z and requires changelog updates for every versioned-file modification.

  • Major: compatibility breaks and broad architecture changes.
  • Minor: relevant new capabilities and flows.
  • Patch: fixes and documentation/process improvements.
Release states: in_preparation, in_validation, published, canceled.
A version can be marked published only when cited plans are in Plans/completed/ and validations are documented.

7) AI, AICC and ASE

AICC (context compression)

  • Creates chronological synthesis per session in wiki/sessions/S*.md.
  • Reduces token cost via structured handoff.
  • Allows fast continuation without re-reading the entire repository.

ASE (skills engine)

  • Loads skills on demand (JIT), never in the initial prompt.
  • Includes release, wiki lint, commit, and formatting skills.
  • Improves consistency while preserving context window.

References: AI.md, CONTEXT_MAP.md, skills/README.md, wiki/schema.md.

8) Security and data

  • Do not version credentials, private data, or temporary artifacts.
  • Validate path traversal on any dynamic path read/write workflow.
  • Keep .env and variants out of version control (allow .env.example only).
  • Record limitations and residual risk when closing plans.

9) Validation and audit

Validation is risk-proportional and must be recorded with evidence.

RiskMinimum expected level
R1 / R2Local checks plus links/consistency review.
R3Shared-flow validation and local regression checks.
R4 / R5Complete validations focused on security, data, and rollback.
