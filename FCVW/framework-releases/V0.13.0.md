# FCVW V0.13.0

## Summary

Reconstructs FCVW as a clean, reusable governance framework, extracts only reviewed generic learning from prior comparison evidence, removes the production-derived fixture from the project, makes preservation of existing behavior an explicit completion contract, and closes selective-reading and adoption-documentation gaps.

## Framework surfaces added

- Ownership and upgrade contracts: `OWNERSHIP.md`, `FRAMEWORK_LOCK.md`, `SCHEMAS.md`, and `MIGRATIONS.md`.
- Safe memory lifecycle: `MEMORY.md` and `wiki/archive/`.
- Separate framework release namespace: `framework-releases/`.
- Optional zero-dependency validator: `tools/validate_fcvw.py`.
- Small governance example: `examples/minimal-change/`.
- Canonical Apache-2.0 license text and `NOTICE`.
- Regression governance: `REGRESSION_GUARDS.md`, plan schema `fcvw/plan@2`, Regression gate, risk matrix, watcher triggers, and `fcvw/regression@1` knowledge records.
- Validator regression suite: `tools/test_validate_fcvw.py`.
- Event-, session-, section-, and skill-type reading routes with deterministic orphan detection.

## Framework surfaces changed

- Operational entrypoint, context routing, planning, versioning, release, token budget, automation, and governance gates.
- Project profiles now declare ownership and instantiation state.
- Skills use `fcvw/skill@1` metadata, provider-neutral language, and explicit operational contracts.
- Wiki records use collision-resistant identifiers and incremental validation.
- `FILESYSTEM.md` is a generated path contract rather than a manual inventory of every historical record.
- New and substantively reopened plans require a completed Regression impact contract; legacy `fcvw/plan@1` records remain readable.
- Canonical document metadata and skill body contracts are now validator-enforced.
- Specialist agent knowledge uses collision-resistant wiki identity instead of shared fixed journal filenames.
- Git/release skill behavior now separates application/framework namespaces and requires explicit authority for external mutations.
- The root README now explains adoption modes, lifecycle, ownership, selective reading, validation profiles, automation scenarios, namespaces, limitations, and navigation.
- `incremental` validation now implements an exact, expiring legacy baseline; `strict` rejects baseline use and blocks all applicable findings.
- The operational index catalogs all root policies and project profiles; the clean profile rejects unexpected root entries.
- Token-budget and AI isolation guidance now preserve cumulative mandatory reading triggers.

## Framework surfaces removed

- Application-owned plans, changelogs, audits, troubleshooting, wiki history, session history, media, and duplicate license copied into the clean `FCVW/` baseline.
- Duplicate framework-governance README.
- Root folder `FCVW - Exemplo retirado de aplicação real/`: 1,099 files, 55 directories, and 3,278,999 bytes removed after exact-path and reparse-point verification.
- Application-specific end-to-end runtime commands and local UI assumptions left in reusable `TESTS.md`.

## Ownership and path changes

The framework now distinguishes replaceable policies, protected project profiles, append-only records, generated indexes, and templates. Production-derived comparison evidence is outside the framework project and distributable artifact. Framework releases no longer share the application changelog namespace.

## Schema changes

Introduces versioned schemas for plans, application changelogs, framework releases, wiki pages, skills, automation contracts, confirmed regressions, and legacy validation baselines. `fcvw/plan@2` adds the mandatory regression contract without silently changing historical `fcvw/plan@1` meaning. Existing downstream records are not bulk-rewritten; adoption uses an explicit legacy baseline and migration plan.

## Migration

Follow `FCVW/MIGRATIONS.md`. Preserve downstream project profiles and records, replace framework-owned policies only after reviewing local modifications, move any FCVW version records out of application changelogs, remove comparison fixtures from the installed project, adopt `fcvw/plan@2` for new or reopened work, and validate the selected profile.

## Downstream preservation rules

Never replace completed project profiles, application records, secrets, runtime artifacts, or local history during a framework upgrade. Resolve local modifications using `OWNERSHIP.md` and record any intentional divergence.

## Known gaps

- The validator is intentionally optional and standard-library-only; it does not replace application-specific tests.
- Markdown governance cannot force an arbitrary external agent or provider adapter to honor reading routes; integrations must follow `AGENTS.md`.
- Executable CI and provider automation remain Scenario 2/3 project decisions rather than implicit Scenario 1 behavior.

## Rollback

Restore the prior V0.12.0 package from a verified release artifact. If the removed comparison data is still needed for research, restore it only to a separate non-distribution workspace from its user-controlled source.
